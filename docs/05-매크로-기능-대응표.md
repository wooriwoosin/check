# 05. 기존 매크로 기능 대응표

> **"전임자가 짠 로직이 뭐가 뭔지 몰라서 손을 못 대겠다"** 에 대한 답입니다.
> 기존 `결합접수_검수.xlsm` 의 **모든 기능**을 하나도 빠짐없이 정리하고,
> 각각이 지금 **어디로 갔는지 / 왜 바뀌었는지** 를 적었습니다.

---

## 한눈에 보기

| | 기존 매크로 | 지금 |
|---|---|---|
| 기능 수 | **10개** | **17개** (기존 10개 전부 유지 + 신규 7개) |
| 결합 판정 | 결합시트 대조만 | 웹에서 결합 **요청**을 먼저 감지 → 전산에서 대조 |
| 실행 위치 | KT전산 안에서만 | 웹 1차 → KT전산 2차 |
| 실행 방식 | 버튼 3개를 순서대로 | 웹: 파일 올리기 / 전산: 붙여넣기 |
| 결과 표시 | 셀 배경색 (필터·집계 불가) | 글자 (필터·집계 가능) |
| 통신사 필터 | 없음 (손으로 걸렀음) | 자동 |

**기존 기능은 하나도 버리지 않았습니다.** 7개는 웹 1차로 옮겼고, 3개는 전산 2차에 그대로 있습니다.

## 1. 기존 매크로 기능 10개 — 어디로 갔나

### 매크로 01 — `검수_01_접수결합매칭_최종`

| ID | 기능 | 원래 로직 | 지금 | 어디에 |
|---|---|---|---|---|
| **M1-1** | **결합여부** | 웹 주민번호(AE)·사업자번호(BL) 앞 6자리가 결합시트 R(생년월일)에 있으면 `O` | ✅ 유지 + **수정** | 2차 `웹` 시트 `결합검수` 열 |
| **M1-2** | **접수검수** | 웹 상품옵션(D) 정규화 == 접수 상품명(AK) 정규화 → `O`/`상품상이`/`접수 X` | ✅ 유지 + **정규화 재작성** | 2차 `웹` 시트 `접수검수` 열 |
| **M1-3** | **최종판정** | 결합+접수 조합 → `정상`/`결합누락`/`접수누락`/`접수·결합 누락` | ✅ 유지 + **개선** | 2차 `웹` 시트 `2차오류사유`·`2차판정` 열 |
| **M1-4** | **웹미존재_접수건** | 접수에는 있는데 웹 H에 매칭 키가 없는 건을 별도 시트로 | ✅ 유지 | 2차 `접수` 시트 **AZ열**을 `웹없음` 으로 필터 |

#### M1-1 이 어떻게 바뀌었나
- **`BL` → `BK`**: 매크로는 사업자번호를 `BL`에서 읽었는데 **실제 웹 데이터에 BL 열은 없습니다** (헤더가 한 칸 밀려 있었음). 그래서 법인 결합은 **한 번도 매칭된 적이 없습니다.**
- **결합 요청 감지 추가**: 결합시트에 없으면 그냥 `결합X` 였는데, 이제 1차에서 감지한 `결합대상` 과 교차해서 **`결합누락`** 을 짚어줍니다.

#### M1-2 가 어떻게 바뀌었나
정규화 함수가 **KT 유선 356건 중 89건(25.0%)** 에서 틀렸습니다. 다시 썼습니다.

| 상품옵션 | 기존 결과 | 지금 |
|---|---|---|
| `(하브)TV에센스(+1G)` | ❌ `에센스` (TV인데 인터넷이 됨) | ✅ `TV에센스` |
| `TV에센스(+500M)` | ❌ `베이직` | ✅ `TV에센스` |
| `패밀리슬림(100M)` | ❌ `슬림` (패밀리 유실) | ✅ `패밀리슬림` |
| `(협력)T베이직→모든G` | ❌ 빈값 | (이관 제외 대상) |
| `원스톱해지(OSS)` | ❌ 빈값 | ✅ `원스톱해지` |

지금은 **이관 대상 274건 전부 정규화 성공(실패 0건)** 입니다.

#### M1-3 이 어떻게 바뀌었나
- 기존: 결합/접수 두 축만 봐서 4가지 결과. **셋트유형(단독/DPS)을 안 봐서 단독 49건이 전부 `결합누락`** 이었습니다.
- 지금: `2차오류사유` 에 `상품상이` `개통상태불일치` `결합누락` `원스톱미접수` 를 **글자로 나열**하고, `2차판정` 은 `정상`/`확인필요` 두 개뿐입니다. 필터가 됩니다.

### 매크로 02 — `검수_02_부가검수_오류만표시`

| ID | 기능 | 원래 로직 | 지금 | 어디에 |
|---|---|---|---|---|
| **M2-1** | **업체 검수** | 웹 접점코드(AB, 괄호제거) == 접수 접점명(I, `우리정보통신_`·`주식회사 `·`(주)` 제거) | ✅ 유지 | **2차** `웹` 시트 `접수접점명` 열 |
| **M2-2** | **상부점** | AB가 `(KT)온라인` → AA는 `1.유KT-우리(온라인)(월☆통15)`, 그 외는 `1.유KT-우리(도매)(동판O)` | ✅ **1차로 이동** + 규칙 수정 | 1차 `상부점` 탭 |
| **M2-3** | **개통기한** | 개통기한(P) == 접수일(S)의 익월 말일 | ✅ **1차로 이동** | 1차 `개통기한` 탭 |
| **M2-4** | **판매점** | 협력점(Q)에 `□`/`■` → 접수경로(AX)는 `5.판매점☆` | ✅ **1차로 이동** + `☆★` 규칙 추가 | 1차 `판매점 접수경로` 탭 |
| **M2-5** | **개통상태** | 접수 진행상태(U) ↔ 웹 개통상태(L) | ✅ 유지 + 값 추가 | **2차** `웹` 시트 `개통상태검수` 열 |

#### M2-2 가 어떻게 바뀌었나
기존 규칙은 값 2개만 인정해서 **`대성(상권사업부)` 8건이 전부 오탐**이었습니다. (지금은 대성이 이관 제외라 아예 안 걸립니다)

지금 규칙은 두 단계입니다.

| 단계 | 규칙 | 어디서 |
|---|---|---|
| 1차 | **상부점이 온라인 ↔ 접점코드도 온라인** | 웹 |
| 1차 | **상품명이 `유선기타_*` ↔ 상부점도 `유선기타`** | 웹 |
| 1차 | 접점코드가 `(KT)도매`(우리 직영) → 상부점에 `도매` | 웹 |
| **2차** | **도매 하위 접점이 실제로 전산에 맞게 들어갔는지** | KOS 접점명(I)과 대조 |

말씀하신 그대로입니다 — **도매는 접점이 24종이라 웹만으로는 못 가립니다.**
실제로 맞는 접점으로 접수됐는지는 KOS `접점명` 을 봐야 알 수 있어서 2차에 뒀습니다.

> ⚠️ **접점코드별 "통상 상부점" 을 데이터에서 학습하면 안 됩니다.**
> 업체 접점은 각자 상부점이 다르고, 같은 `(KT)도매` 라도 상품에 따라 갈립니다.
> (예: `주식회사 힐링케어에듀` — 접점 `(KT)도매` 인데 상부점은 `1.유KT-우리(유선기타)(월☆통15)` 가 정상)
> 처음엔 다수결로 학습했다가 이 건이 오탐으로 잡혀서 규칙을 위 3개로 바꿨습니다.

#### M2-4 가 어떻게 바뀌었나
기존은 `□■` **한 방향만** 봤습니다. 이제 양쪽 다 봅니다.

| 협력점명 표기 | 접수경로가 이래야 함 | 현재 데이터 |
|---|---|---|
| `☆` 또는 `★` | **협력점** (`0.협력점★`) | 193건, 위반 0 |
| `□` `■` `□□` `■■` | **판매점** (`5.판매점☆`) | 33건, 위반 0 |
| 표기 없음 | 온라인 유입 (인스타·유튜브·구글 등) — 검증 대상 아님 | 48건 |

#### M2-5 에 값을 추가했습니다
| KOS 진행상태 | 정상인 웹 개통상태 | 비고 |
|---|---|---|
| 사용중 | 개통완료 | 그대로 |
| 가설중(예약) | 접수완료 / 실적확인중 / **접수대기** | `접수대기` 추가 |
| 해지 | 해지(철회)완료 / 해지(철회)중 / 취소완료 | 그대로 |

### N-3 OSS(원스톱전환) — 새로 만든 것

기존 매크로에는 **원스톱 코드가 한 줄도 없었습니다.** `접수` 시트에 `V열: 원스톱전환여부` 헤더만 있고 VBA는 V열을 한 번도 읽지 않았습니다.

**마스킹 방식이 달라서 기존 "앞 8자리" 키로는 매칭이 안 됩니다.**

```
접수리스트 X : z!66251240***   → 앞 8자리
원스톱     H : z!6825***2039   → 앞4 + 뒤4   ← 별도 키가 필요
```

그래서 원스톱 전용 키(`앞4+뒤4`)를 새로 만들었습니다.

| 검수 | 내용 |
|---|---|
| 1차 `OSS(원스톱전환)` 탭 | 웹 원스톱해지 라인 전체 + 원스톱키 + 키 생성 실패 경고 |
| 2차 `OSS대사` 시트 | 웹 라인 수 ↔ KOS 원스톱 행 수 **차이가 0이어야 정상** |
| 2차 `OSS대사` 시트 | 웹에만 있음 → `원스톱없음` (= KOS 미접수) |
| 2차 `원스톱` 시트 R열 | KOS 에만 있음 → `웹없음` |

**실제 검증**: 웹 OSS 18건 중 KOS 샘플 9건과 **8건이 키로 정확히 매칭**됐습니다.
남은 1건(김가현)은 웹 가입번호가 `z!664254412912` 로 **12자리 오타** — 1차의 `가입번호` 경고와 정확히 교차검증됐습니다.

## 3. 버그로 없앤 것 (기능이 아니라 오작동)

| 원래 코드 | 왜 없앴나 |
|---|---|
| `PickWebKey8` 의 **마지막 4자리 폴백** | 서비스번호가 아니라 **전화번호 끝자리**로 매칭해서 엉뚱한 고객에게 붙었습니다 |
| `ExtractKey8Candidates` 가 **첫 숫자뭉치**를 사용 | 실제 서비스번호는 **`z!` 가 붙은 쪽**입니다. 24건이 인터넷계약번호로 잘못 매칭됐습니다 |
| `WEB_BL = "BL"` (사업자번호) | **존재하지 않는 열**입니다. 실제 위치는 `BK` |
| 결합 매칭이 **생년월일 6자리 단독** | 같은 날 태어난 사람이 있으면 오매칭. (지금도 KOS 결합리스트에 전화번호가 안 내려와서 6자리뿐입니다 — 개선 여지) |
| 결과를 **셀 배경색**으로만 표시 | 왜 틀렸는지 사유가 안 남고 필터·집계가 안 됩니다 |
