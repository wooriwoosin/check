## 1. 파일 구조

### 시트 4개

| 시트 | 데이터 시작행 | 용도 | 붙여넣는 원본 |
|---|---|---|---|
| `웹` | **2행** | 우리 어드민 로우데이터 | 전체고객상품(YYYYMMDDHHMM).xls |
| `접수` | **3행** | KT전산 접수리스트 | KOS 접수리스트 양식.xlsx |

| `웹미존재_접수건` | 2행 | 매크로가 **생성**하는 결과 시트 | (자동생성) |

| # | 프로시저 | 하는 일 |
|---|---|---|

| 01 | `검수_01_접수결합매칭_최종` | 결합여부(BM) / 접수검수(BN) / 최종판정(BO) 채움 + `웹미존재_접수건` 시트 생성 |
| 02 | `검수_02_부가검수_오류만표시` | 업체명·상부점·개통기한·판매점·개통상태 5개 항목을 **셀 배경색**으로만 표시 |

## 2. 매크로 01 — 접수/결합 매칭 로직

### 2-1. 매칭 키: "숫자 8자리"

KT전산 접수리스트의 서비스번호(X열)는 **마스킹**되어 있습니다.

```
KT전산 X열 : z!66251240***      → 숫자만 뽑으면 "66251240" (8자리)
웹    H열 : z!61251458334 / 053-016-2406  → 앞 숫자뭉치 "61251458334" → 앞 8자리 "61251458"
```

그래서 **양쪽 다 앞 8자리 숫자**를 키로 잡습니다. 이 설계 자체는 맞습니다.

### 2-2. 결합여부(BM) 판정

```
결합시트 R열(생년월일 6자리) 전부를 딕셔너리에 담아두고
  웹 AE(주민번호) 앞 6자리가 있으면          → "O"
  또는 웹 BL(사업자번호) 앞 6자리가 있으면    → "O"
  아니면                                    → "결합 X"
```

### 2-3. 접수검수(BN) 판정

웹 D열(상품옵션)과 접수 AK열(상품명)을 각각 정규화해서 비교합니다.

| | 정규화 규칙 |
|---|---|
| 웹 D열 | `(추단)` 제거 → `TV모든G` 우선판정 → 공백/괄호/`+` 제거 → `TV베이직`/`패밀리베이직`/`오피스넷` 순 판정 → 최후에 속도(`100M`→슬림 / `500M`→베이직 / `1G`→에센스) |
| 접수 AK열 | `"지니"`, `"인터넷"`, 공백 제거 |

결과: `O` / `상품상이`(웹 D열 노란색) / `접수 X`

### 2-4. 최종판정(BO)

| 결합 | 접수 | 최종판정 |
|---|---|---|
| O | O | 정상 |
| X | O | 결합누락 |
| O | 접수X | 접수누락 |
| X | 접수X | 접수·결합 누락 |
| 그 외 | | 확인필요 |

## 3. 매크로 02 — 부가검수 5종

복합키 `서비스번호8자리_전화번호앞5자리` 로 웹↔접수를 매칭한 뒤 검사합니다.
(웹 AG 명의자연락처 / 접수 AF 고객연락처. 마스킹된 `010-82**-*265` 도 앞 5자리 `01082` 는 살아있어서 동작함)

| # | 항목 | 규칙 | 표시 |
|---|---|---|---|
| 1 | 업체명 | 웹 AB(괄호내용 삭제) == 접수 I(`우리정보통신_`,`주식회사 `,`(주)` 제거) | AB 셀 색 |
| 2 | 상부점 | AB가 `(KT)온라인` → AA는 `1.유KT-우리(온라인)(월☆통15)`<br>그 외 → AA는 `1.유KT-우리(도매)(동판O)` | AA 셀 색 |
| 3 | 개통기한 | P == 접수일(S)의 **익월 말일** | P 셀 색 |
| 4 | 판매점 | 협력점(Q)에 `□`/`■` 포함 → 접수경로(AX)는 `5.판매점☆` | AX 셀 색 |
| 5 | 개통상태 | 접수 U `사용중`→L `개통완료` / `가설중(예약)`→`접수완료`·`실적확인중` / `해지`→`해지(철회)완료`·`해지(철회)중`·`취소완료` | L 셀 색 |

## 4. ⚠️ 발견된 버그 / 문제점

### 🔴 치명적

#### B-1. `웹` 시트 헤더가 데이터보다 **한 칸 밀려 있음** (BB열부터)

실제 붙여넣은 280행 데이터를 검증한 결과:

| 열 | 헤더에 적힌 이름 | **실제 들어있는 데이터** | 근거 |
|---|---|---|---|
| BB | 고객이력 | 최초등록일 (일시) | 전 행에 일시값 |
| BC | 최초등록일 | 이메일 | `katoy@naver.com` |
| BD | 이메일 | 인입최초시간 | |
| BE | 인입최초시간 | **취소요청일** | 값이 있는 44행 = `취소완료` 44행과 **정확히 일치** |
| BI | 소개자 | 대표자 | |
| BJ | 대표자 | 유선동판 명의자 | |
| BK | 유선동판 명의자 | **사업자번호** | `8538601713` (10자리) |
| BL | **사업자번호** | *(완전히 비어있음)* | |

**결과: 매크로 01이 사업자번호로 결합을 찾는 `WEB_BL = "BL"` 코드가 항상 빈 값을 읽습니다.**
→ 법인/사업자 고객은 결합이 있어도 **무조건 `결합 X`** 로 찍힙니다. 이 분기는 사실상 죽은 코드입니다.

> 원인 추정: 헤더 행에 `고객이력` 열이 하나 더 적혀 있는데, 실제 웹 다운로드 파일에는 그 열이 없습니다.
> **7번 요청사항인 "고객이력란에 결합이력" 체크가 지금 데이터로는 아예 불가능**합니다. (아래 A-1 참고)

#### B-2. `PickWebKey8` 의 "마지막 4자리" 폴백 → **엉뚱한 고객과 매칭**

8자리 키로 못 찾으면, 웹 H열 **전체 숫자**의 마지막 4자리로 접수 키를 훑습니다.

```
웹 H = "z!61251458334 / 053-016-2406"
전체 숫자 = 612514583340530162406  →  마지막 4자리 = "2406"   ← 전화번호 꼬리!
```

서비스번호가 아니라 **전화번호 끝자리**로 매칭합니다. 8자리 접수키 중 끝 4자리가 우연히 같은
**아무 관계없는 다른 고객의 접수 건**에 붙어버립니다. 상품상이/정상 판정이 통째로 오염됩니다.

#### B-3. 결합 매칭이 **생년월일 6자리 단독** — 동명이인 충돌

`결합` 시트 R열(생년월일)만으로 매칭합니다. 이름·전화번호를 안 씁니다.
같은 날 태어난 사람이 결합 리스트에 있으면 **결합 안 한 고객이 `결합 O`** 로 찍힙니다.
KOS 결합 양식에는 Q(고객명), S(전화번호)가 같이 있는데 안 쓰고 있습니다.

### 🟠 상품 정규화 오류 (실데이터 280행 검증)

매크로 정규화 함수를 그대로 돌려본 결과입니다.

| 웹 상품옵션 | 매크로 결과 | 판정 | 건수 |
|---|---|---|---|
| `TV에센스(+500M)` | **`베이직`** | ❌ TV 판정 실패 → 500M에 걸려 인터넷 베이직이 됨 | 1 |
| `(추단)TV에센스↑` | **`(빈값)`** | ❌ 어디에도 안 걸림 | 1 |
| `패밀리슬림(100M)` | **`슬림`** | ❌ 접수 리스트는 "인터넷 패밀리 슬림" → 상품상이 오탐 | 5 |
| `패밀리베이직(500M)` | **`베이직`** | ❌ 코드가 `패밀리베이직 → 베이직` 으로 **일부러 지움** | 4 |
| `패밀리에센스(1G)` | **`에센스`** | ❌ 동일 | 2 |
| `원스톱해지(OSS)` | **`(빈값)`** | ❌ 부가상품 미지원 | 20 |
| `인터넷전화(번동)` | **`(빈값)`** | ❌ | 2 |
| `일반전화(신규)` | **`(빈값)`** | ❌ | 1 |

**280건 중 36건(12.9%)** 이 상품 정규화 단계에서 이미 틀립니다.

원인은 `TV에센스` 케이스 누락 + 마지막 속도 판정이 `ElseIf` 가 아니라 **연속된 `If`** 여서
문자열에 `500M`이 있으면 TV상품인데도 인터넷 상품으로 덮어써지는 구조입니다.

### 🟡 검수 규칙 자체가 현실과 안 맞음

#### C-1. 상부점(AA) 규칙이 값 2개만 인정 → **6건 오탐**

```
AB='대성(상권사업부)'  AA='5.유KT-대성_평택(월☆통20)'   ← 정상 데이터인데
```
`(KT)온라인` 이 아니면 무조건 `1.유KT-우리(도매)(동판O)` 를 요구해서 이 6건이 전부 경고로 칠해집니다.
접점코드 → 상부점 **매핑 테이블**로 바꿔야 합니다.

#### C-2. 셋트유형(G)을 **아예 안 봄** → 결합누락 대량 오탐

이번 데이터 280건 구성:

| 셋트유형 | 건수 |
|---|---|
| DPS 계열 (`DPS`,`DPS(1~3)`) | **231** |
| 단독 (`단독`,`단독(2)`) | **49** |

**단독 49건은 원래 결합이 없는 게 정상**인데, 매크로는 전부 `결합 X` → `결합누락` 으로 찍습니다.
사장님이 지적하신 7번 항목이 바로 이겁니다.

#### C-3. 원스톱(OSS) 로직은 **매크로에 존재하지 않음**

> "원스톱을 매크로에서 잡던데 뭐때문에 잡는지 의미가없어"

확인 결과 — **매크로에 원스톱 코드는 한 줄도 없습니다.**
`접수` 시트에 `V열: 원스톱전환여부` 헤더가 있을 뿐이고, VBA는 V열을 **한 번도 읽지 않습니다.**
KOS 원스톱 양식을 붙일 시트조차 없습니다. (만들다 만 흔적으로 보입니다)

#### C-4. 개통상태 매핑에 `보류`, `접수대기` 없음
웹 개통상태 실제 분포에 `보류` 14건, `접수대기` 2건이 있는데 대응 규칙이 없어 그냥 경고 처리됩니다.

### 🟢 사소한 문제

| | 내용 |
|---|---|
| D-1 | 매크로 01이 칠한 **웹 D열 노란색을 초기화하지 않음** → 02는 초기화하는데 01만 안 함. 재실행 시 지워진 오류가 계속 남음 |
| D-2 | 결과가 **셀 배경색**뿐이라 "왜 틀렸는지" 사유가 안 남음. 필터링/집계 불가 |
| D-3 | 상수명 오류: `ACC_B As String = "AE"` (이름은 B인데 값은 AE), `COMB_R` 주석은 "주민번호"인데 실제는 생년월일 |
| D-4 | `Range(...).Value` 셀 단위 접근 → 280행 × 67열이면 느림. 배열 일괄 읽기로 바꾸면 수십 배 빠름 |
| D-5 | 웹 AG(명의자 연락처)가 비면 02 검수가 **조용히 통과**됨 (설치연락처 AF 폴백 없음) |
