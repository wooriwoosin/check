## 1. 파일 구조

| `접수` | **3행** | KT전산 접수리스트 | KOS 접수리스트 양식.xlsx |

## 2. 매크로 01 — 접수/결합 매칭 로직

### 2-1. 매칭 키: "숫자 8자리"

KT전산 접수리스트의 서비스번호(X열)는 **마스킹**되어 있습니다.

```
KT전산 X열 : z!66251240***      → 숫자만 뽑으면 "66251240" (8자리)
웹    H열 : z!61251458334 / 053-016-2406  → 앞 숫자뭉치 "61251458334" → 앞 8자리 "61251458"
```

그래서 **양쪽 다 앞 8자리 숫자**를 키로 잡습니다. 이 설계 자체는 맞습니다.

### 2-2. 결합여부(BM) 판정

```
결합시트 R열(생년월일 6자리) 전부를 딕셔너리에 담아두고
  웹 AE(주민번호) 앞 6자리가 있으면          → "O"
  또는 웹 BL(사업자번호) 앞 6자리가 있으면    → "O"
  아니면                                    → "결합 X"
```

### 2-3. 접수검수(BN) 판정

웹 D열(상품옵션)과 접수 AK열(상품명)을 각각 정규화해서 비교합니다.

| | 정규화 규칙 |
|---|---|
| 웹 D열 | `(추단)` 제거 → `TV모든G` 우선판정 → 공백/괄호/`+` 제거 → `TV베이직`/`패밀리베이직`/`오피스넷` 순 판정 → 최후에 속도(`100M`→슬림 / `500M`→베이직 / `1G`→에센스) |
| 접수 AK열 | `"지니"`, `"인터넷"`, 공백 제거 |

결과: `O` / `상품상이`(웹 D열 노란색) / `접수 X`

### 2-4. 최종판정(BO)

| 결합 | 접수 | 최종판정 |
|---|---|---|
| O | O | 정상 |
| X | O | 결합누락 |
| O | 접수X | 접수누락 |
| X | 접수X | 접수·결합 누락 |
| 그 외 | | 확인필요 |

## 3. 매크로 02 — 부가검수 5종

복합키 `서비스번호8자리_전화번호앞5자리` 로 웹↔접수를 매칭한 뒤 검사합니다.
(웹 AG 명의자연락처 / 접수 AF 고객연락처. 마스킹된 `010-82**-*265` 도 앞 5자리 `01082` 는 살아있어서 동작함)

| # | 항목 | 규칙 | 표시 |
|---|---|---|---|
| 1 | 업체명 | 웹 AB(괄호내용 삭제) == 접수 I(`우리정보통신_`,`주식회사 `,`(주)` 제거) | AB 셀 색 |
| 2 | 상부점 | AB가 `(KT)온라인` → AA는 `1.유KT-우리(온라인)(월☆통15)`<br>그 외 → AA는 `1.유KT-우리(도매)(동판O)` | AA 셀 색 |
| 3 | 개통기한 | P == 접수일(S)의 **익월 말일** | P 셀 색 |
| 4 | 판매점 | 협력점(Q)에 `□`/`■` 포함 → 접수경로(AX)는 `5.판매점☆` | AX 셀 색 |
| 5 | 개통상태 | 접수 U `사용중`→L `개통완료` / `가설중(예약)`→`접수완료`·`실적확인중` / `해지`→`해지(철회)완료`·`해지(철회)중`·`취소완료` | L 셀 색 |

## 4. ⚠️ 발견된 버그 / 문제점

### 🔴 치명적

#### B-1. `웹` 시트 헤더가 데이터보다 **한 칸 밀려 있음** (BB열부터) — ✅ 원본 대조로 확정

**보안 풀린 웹 로우데이터(979행 × 63열)로 확인했습니다.**
실제 웹 다운로드에는 **`고객이력` 컬럼이 존재하지 않습니다.** (사장님 말씀대로 고객이력 = `기타`(BA) 내용)
매크로 `웹` 시트 헤더에만 `고객이력`이 하나 더 끼어 있어서, BB열부터 전부 한 칸씩 밀렸습니다.

| 열 | 매크로 헤더 | **실제 웹 로우데이터** |
|---|---|---|
| BA | 기타 | 기타 ✅ |
| BB | ~~고객이력~~ | **최초등록일** |
| BC | 최초등록일 | **이메일** |
| BD | 이메일 | **인입최초시간** |
| BE | 인입최초시간 | **취소요청일** |
| BF | 취소요청일 | **단말기명** |
| BG | 단말기명 | **토스자** |
| BH | 토스자 | **소개자** |
| BI | 소개자 | **대표자** |
| BJ | 대표자 | **유선동판 명의자** |
| BK | 유선동판 명의자 | **사업자번호** ← 실제 위치 |
| BL | **사업자번호** | **(열 자체가 없음)** |

**결과: 매크로 01의 `WEB_BL = "BL"` 은 존재하지도 않는 열을 읽습니다.**
→ 사업자번호 기반 결합 매칭은 100% 동작하지 않습니다. 법인/사업자 고객(28건)은 결합이 있어도 무조건 `결합 X`.

#### B-2. `PickWebKey8` 의 "마지막 4자리" 폴백 → **엉뚱한 고객과 매칭**

8자리 키로 못 찾으면, 웹 H열 **전체 숫자**의 마지막 4자리로 접수 키를 훑습니다.

```
웹 H = "z!61251458334 / 053-016-2406"
전체 숫자 = 612514583340530162406  →  마지막 4자리 = "2406"   ← 전화번호 꼬리!
```

서비스번호가 아니라 **전화번호 끝자리**로 매칭합니다. 8자리 접수키 중 끝 4자리가 우연히 같은
**아무 관계없는 다른 고객의 접수 건**에 붙어버립니다. 상품상이/정상 판정이 통째로 오염됩니다.

#### B-3. 결합 매칭이 **생년월일 6자리 단독** — 동명이인 충돌

`결합` 시트 R열(생년월일)만으로 매칭합니다. 이름·전화번호를 안 씁니다.
같은 날 태어난 사람이 결합 리스트에 있으면 **결합 안 한 고객이 `결합 O`** 로 찍힙니다.
KOS 결합 양식에는 Q(고객명), S(전화번호)가 같이 있는데 안 쓰고 있습니다.

#### B-4. **`z!` 마커를 무시함 → 24건이 엉뚱한 번호로 매칭** 🆕

가입.번호(H)에 숫자뭉치가 2개 이상 들어있는 행이 **30건** 있습니다.
그리고 실제 서비스번호에는 **`z!` 접두사가 붙어 있습니다.** (299건 전부)

```
r13  61250677816/Z!67253719883 / 02-0041-5544
     └ 인터넷계약번호            └ ★진짜 서비스번호
     매크로가 잡는 키: 61250677      실제 키: 67253719
```

매크로 `ExtractKey8Candidates` 는 **왼쪽부터 순서대로** 후보를 담고 `PickWebKey8` 이 먼저 맞는 걸 씁니다.
→ `z!` 가 뒤에 있는 **24건**은 앞의 다른 번호로 먼저 매칭됩니다.

특히 위험한 케이스:
```
r15  63250668734/z!63250669162/031-117-9227
     앞 8자리: 63250668  vs  63250669   ← 1 차이. 같은 고객의 다른 회선이라 둘 다 접수리스트에 있음
```
**같은 고객의 다른 상품 라인에 붙어서 `상품상이` 오탐이 납니다.**

→ **`z!` 뒤 번호를 최우선으로 잡아야 합니다.**

### 🟠 상품 정규화 오류 — **KT 유선 356건 중 89건(25.0%) 오작동**

전체 로우데이터(979행)에서 KT 유선 356건만 뽑아 매크로 정규화 함수를 그대로 돌린 결과입니다.

| 웹 상품옵션 | 매크로 결과 | 뭐가 틀렸나 | 건수 |
|---|---|---|---|
| `(협력)T베이직→모든G` | **`(빈값)`** | 업셀링/전환 상품 미지원 | 22 |
| `500M→1G` | **`에센스`** | 전환 상품인데 속도만 보고 판정 | 20 |
| `(하브)TV에센스(+1G)` | **`에센스`** | **TV인데 인터넷 에센스가 됨** | 17 |
| `(자체)T베이직→모든G` | **`(빈값)`** | | 8 |
| `패밀리슬림(100M)` | **`슬림`** | `패밀리` 유실 | 5 |
| `패밀리베이직(500M)` | **`베이직`** | 코드가 `패밀리베이직 → 베이직` 으로 **일부러 지움** | 4 |
| `(하브)TV초이스↑(+1G)` | **`에센스`** | TV인데 인터넷이 됨 | 3 |
| `인터넷전화(번동)` | **`(빈값)`** | | 2 |
| `패밀리에센스(1G)` | **`에센스`** | `패밀리` 유실 | 2 |
| `(협력)T라이트→모든G` / `(추단)TV에센스↑` / `TV에센스(+500M)` / `일반전화(신규)` / `인터넷전화(자사번호번동)` / `프리미엄(2.5G↑)` | 빈값 또는 오판 | | 각 1 |

**합계 89건 / 356건 = 25.0%** 가 상품 비교 단계에서 이미 틀립니다.

원인 3가지:
1. **`TV에센스`, `TV초이스` 분기 자체가 없음** — `TV모든G`, `TV베이직` 두 개만 처리
2. **마지막 속도 판정이 `ElseIf` 가 아니라 연속된 `If`** — 문자열에 `500M`/`1G` 만 있으면 TV상품인데도 인터넷 상품으로 덮어써짐
3. **업셀링/전환(`→`), 동판, 부가상품(OSS/전화) 미지원**

### 🟡 검수 규칙 자체가 현실과 안 맞음

#### C-1. 상부점(AA) 규칙이 값 2개만 인정 → **8건 오탐** (전체 데이터 기준)

```
AB='대성(상권사업부)' → AA='5.유KT-대성_평택(월☆통20)'      6건
                    → AA='5.유KT-대성_경기서부지사(월☆통20)'  2건   ← 둘 다 정상 데이터
```
`(KT)온라인` 이 아니면 무조건 `1.유KT-우리(도매)(동판O)` 를 요구해서 이 8건이 전부 경고로 칠해집니다.

또한 `(KT)우리정보통신_유선UIT` → `1.무KT-우리(유심)(월☆통말)` (30건) 같은 조합도 있어서,
접점코드 → 상부점 **매핑 테이블**(1:다 허용)로 바꿔야 합니다. 전체 데이터로 뽑아보면 대부분 1:1로 깔끔합니다.

#### C-2. 셋트유형(G)을 **아예 안 봄** → 결합누락 대량 오탐

전체 로우데이터 979건 중 **KT 유선 356건** 구성:

| 셋트유형 | 건수 |
|---|---|
| DPS 계열 (`DPS`,`DPS(1~3)`) | **277** |
| 단독 (`단독`,`단독(2)`) | **79** |

**단독 79건은 원래 결합이 없는 게 정상**인데, 매크로는 전부 `결합 X` → `결합누락` 으로 찍습니다.
사장님이 지적하신 7번 항목이 바로 이겁니다. (실제 결합대상은 5건뿐 — 02 문서 참고)

#### C-3. 원스톱(OSS) 로직은 **매크로에 존재하지 않음**

> "원스톱을 매크로에서 잡던데 뭐때문에 잡는지 의미가없어"

확인 결과 — **매크로에 원스톱 코드는 한 줄도 없습니다.**
`접수` 시트에 `V열: 원스톱전환여부` 헤더가 있을 뿐이고, VBA는 V열을 **한 번도 읽지 않습니다.**
KOS 원스톱 양식을 붙일 시트조차 없습니다. (만들다 만 흔적으로 보입니다)

#### C-4. 개통상태 매핑에 `보류`, `접수대기` 없음
웹 개통상태 실제 분포(979건)에 `보류` 51건, `접수중` 56건, `접수반송` 17건, `개통대기` 9건,
`실사중` 5건, `접수대기` 2건이 있는데 대응 규칙이 없어 전부 경고 처리됩니다.

#### C-5. **타 통신사 건이 섞여 있는데 필터가 없음** 🆕

웹 로우데이터 979건 중 **KT는 408건(41.7%)** 뿐입니다.
나머지는 SKT / SKB / LG U+ / SKYLIFE / HelloVision / 렌탈 건입니다.

매크로는 통신사 필터가 없어서, KT전산에 없는 타사 건까지 전부 `접수 X` → `접수누락` 으로 찍힙니다.
(지금은 사람이 손으로 KT만 걸러서 붙여넣고 있는 것으로 보입니다 — 1차 웹 검수가 자동으로 해줘야 할 일)
